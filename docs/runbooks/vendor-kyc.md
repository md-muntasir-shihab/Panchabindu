# Private vendor documents — local implementation

The vendor profile screen accepts voluntary JPG/PNG/WebP images (maximum 5 MiB), not PDF. It checks signatures, decodes with pixel limits, re-encodes to WebP without metadata, generates the object path on the server and stores in `private-ops-evidence/vendor-kyc/`. It checks the bucket is private before every upload/download. Vendor identity comes from the verified server session; only the owning vendor and a super admin can access document data. Downloads are proxied via authenticated no-store endpoints rather than public or signed links. Super admin can approve/reject each document; rejection needs a reason. Upload, viewing and review are audited without storing document content, path or original filename in audit entries. The API stores minimal metadata inside the existing `erp-phase4b-store.json` runtime document and registers object cleanup for transaction failures; the ten-document contract is unchanged.

This is **not** a complete KYC decision system: no legal requirements are implied; document type requirements, identity/expiry verification, retention/deletion and access review need policy review. Document approval does not automatically activate a vendor. Do not include personal data in review notes. A private bucket must exist and service-role secrets stay server-only; an unavailable or public bucket fails closed. Do not create or modify live buckets or deploy without explicit authorization.

Tests use disposable state and mocked storage; real Supabase upload/download, storage policy denial, rollback under real database conflict, expiry/retention and browser responsiveness are NOT_TESTED. Failed or ambiguous uploads attempt compensating deletion, but cleanup failures are not independently reconciled: a private orphan object may require manual inspection. Backup and object lifecycle controls are required before production use.
